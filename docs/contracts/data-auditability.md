# Data Auditability Contract

**Scope:** Data traceability and provenance  
**Invariant:** All generated data must be traceable to its experiment, run, model variant, and question of origin

---

## Contract Statement

Every piece of data generated by the system must be **fully auditable**: traceable back to its exact origin, including which experiment, run, model variant, and question produced it. This enables complete reproducibility and scientific integrity.

---

## Auditability Guarantees

### 1. Response Traceability

Every response record includes complete provenance:

| Field | Purpose |
|-------|---------|
| `response_id` | Unique identifier for this response |
| `run_id` | Which run generated this response |
| `variant_id` | Which model variant was used |
| `snapshot_id` | Which question snapshot was answered |
| `model_id` | Base model identifier (redundant for querying) |
| `question_id` | Original question identifier (redundant for querying) |

**Result:** Any response can be traced to:
- The exact run that generated it
- The exact model variant that answered it
- The exact question snapshot that was presented
- The experiment that contains all of these

### 2. Experimental Context Preservation

Each response carries its complete experimental context:

- **What was presented:** Options are saved exactly as shown to the LLM (including randomization)
- **What was configured:** Randomization Seed, prompts, and model parameters (including Model Seed) are traceable through run and variant — see `docs/status/model-seed-checkpoint-b-design.md`
- **What happened:** Full response text, error details, token counts, latency, timestamps

**Rationale:** Scientific reproducibility requires knowing not just the answer, but the complete conditions under which it was generated.

### 3. Error Traceability

Errors are traced with the same rigor as successful responses:

| Field | Purpose |
|-------|---------|
| `error_id` | Unique identifier for this error |
| `run_id` | Which run encountered this error |
| `variant_id` | Which model variant was being used |
| `snapshot_id` | Which question was being processed |
| `error_type` | Classification of error |
| `error_details` | Full error information |

### 4. Configuration Auditability

All configuration is auditable:

- **Experiment:** `config_json` stores complete frozen configuration
- **Run:** `config` stores run-specific configuration
- **Model Variant:** `config` stores variant-specific configuration
- **Config Hash:** SHA-256 hash enables integrity verification

**Result:** Anyone can verify that an experiment ran with the configuration it claims to have used.

### 4b. Request Fidelity and the Debug Echo (distinct records)

`responses.request_json` is derived from the ONE canonical payload
actually handed to the HTTP transport — see
`docs/status/model-seed-checkpoint-b-design.md`, Part 1. There is no
second, independently-maintained construction of the request payload
anywhere in the system; `request_json` and the real POST body are
guaranteed identical by construction, not by convention.

When debug mode is enabled (`OPENROUTER_DEBUG_ENABLED=true`), OpenRouter
may echo back the transformed request body it actually sent to the
upstream provider (`debug.echo_upstream_body`, a **response-side**
field). This is a fundamentally different record from `request_json`:

| Record | What it represents | Where it lives |
|---|---|---|
| `responses.request_json` | The request BCLLM sent to OpenRouter (includes `"debug": {"echo_upstream_body": true}` when requested — that boolean instruction IS part of our own request) | Derived from the one canonical payload, before the call |
| `responses.raw_response` / `raw_response_consolidated` | What OpenRouter sent back, including the echoed upstream body when debug is on | Captured from the response stream, after the call |

**The echoed upstream body must never overwrite or merge into
`request_json`** — they represent different steps (our request vs. what
OpenRouter forwarded upstream) and must stay distinguishable. No data
returned by the API is discarded before its scientific value is
evaluated: `raw_response` preserves every chunk verbatim, debug or not.

**Secrets:** `request_json` never contains the API key or `Authorization`
header — those exist only in the HTTP transport layer (`httpx`'s
`headers=`), never merged into the JSON body that gets persisted.

### 5. Review Trail

Manual review actions are fully auditable:

| Field | Purpose |
|-------|---------|
| `review_status` | Current review state (`auto`, `manual`, `needs_review`, `reviewed`) |
| `reviewed_at` | Timestamp when review occurred |
| `manual_answer` | Human-corrected answer (if provided) |
| `parse_confidence` | Parser's original confidence level |
| `selected_answer` | Parser's original selected answer |

**Critical:** Original data (`selected_answer`, `parse_confidence`) is **never modified**; review adds new fields without overwriting.

## Data Flow Audit Trail

```
Dataset Questions
    ↓ (snapshot)
Question Snapshots (experiment_id, snapshot_id)
    ↓ (execution)
ExecutionPlan (plan_id, experiment_id, runs, variants, items)
    ↓ (execution)
Response (response_id, run_id, variant_id, snapshot_id)
    ↓ (review, optional)
Review Fields (manual_answer, reviewed_at, review_status)
```

At each step:
- **Identity is preserved** — IDs link entities together
- **Context is captured** — Configuration frozen at each level
- **Provenance is traceable** — Any data point traces back to origin

---

## Logging and Audit Trail

Logs are treated as **scientific data** (per system philosophy):

- Logs include experiment, run, model, and question identifiers
- Logs have multiple depth levels (configurable)
- Logs are crash-safe (written immediately, not buffered unsafely)
- Logs do not expose sensitive data (no API keys, tokens)
- Logs can be separated by experiment (manually, not automated)

**Rationale:** Logs enable debugging execution issues and process failuress; they are part of the research dataset.

## Query Examples

### Trace a response to its origin

```sql
-- Given a response_id, trace everything
SELECT 
    r.response_id,
    r.run_id,
    r.variant_id,
    r.snapshot_id,
    r.model_id,
    r.question_id,
    run.experiment_id,
    e.name AS experiment_name,
    mv.model_id,
    qs.json_question_id,
    qs.question_position
FROM responses r
JOIN runs run ON r.run_id = run.run_id
JOIN experiments e ON run.experiment_id = e.experiment_id
JOIN model_variants mv ON r.variant_id = mv.variant_id
JOIN question_snapshots qs ON r.snapshot_id = qs.snapshot_id
WHERE r.response_id = ?;
```

### Verify configuration integrity

```sql
-- Verify experiment configuration hash
SELECT 
    experiment_id,
    name,
    config_json,
    config_hash,
    -- Verify hash matches config_json
    (config_hash = sha256(config_json)) AS hash_valid
FROM experiments;
```

## Violation Examples

### ❌ WRONG: Missing provenance

```python
# VIOLATION: Response cannot be traced to origin
response = {
    "answer": "A",
    "is_correct": True,
    # Missing: run_id, variant_id, snapshot_id, etc.
}
```

### ✅ CORRECT: Complete provenance

```python
# CORRECT: Full traceability
response = Response(
    response_id=generate_uuid(),
    run_id=run.run_id,
    variant_id=variant.variant_id,
    snapshot_id=snapshot.snapshot_id,
    model_id=variant.model_id,
    question_id=snapshot.json_question_id,
    selected_answer="A",
    is_correct=True,
    # ... all other fields
)
```

### ❌ WRONG: Overwriting review data

```python
# VIOLATION: Original data lost
cursor.execute("""
    UPDATE responses 
    SET selected_answer = ?, parse_confidence = ?
    WHERE response_id = ?
""", (manual_answer, "manual", response_id))
```

### ✅ CORRECT: Preserving original, adding review

```python
# CORRECT: Original data intact, review fields added
cursor.execute("""
    UPDATE responses 
    SET manual_answer = ?, review_status = 'manual', reviewed_at = ?
    WHERE response_id = ?
""", (manual_answer, datetime.now(), response_id))
# selected_answer and parse_confidence unchanged
```
